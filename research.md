# Обратная синхронизация (облако → локальный кеш): исследование вариантов

## Текущая архитектура

```
Cloud ──[REST API]──→ Manager
  ↑                      │
  │  Watchdog (local)    │  Startup scan / full_sync()
  │  on_modified         │  _poll_cloud (новые файлы)
  └──────────────────────┘
```

| Механизм | Направление | Когда |
|----------|------------|-------|
| `full_sync()` (sync.py) | Двусторонняя, MD5+mtime | Только при старте |
| `_startup_scan()` (ui.py) | Локальный → облако (upload) | При старте |
| Watchdog | Локальный → облако (upload) | При изменении файла |
| `_poll_cloud()` (ui.py) | Облако → локальный (download) | Каждые 60с, **НО только для НОВЫХ файлов** |

**Пробел:** если существующий скачанный файл изменился в облаке (через веб-интерфейс, другой клиент, мобильное приложение), Менеджер это **не обнаружит**. Локальная копия останется старой.

## Варианты реализации

### Вариант A: Расширить `_poll_cloud` — проверять не только NEW, но и MODIFIED

**Идея:** `_poll_cloud` уже вызывает `GET /resources/last-uploaded?limit=50`, который возвращает **последние изменённые** файлы на всём диске. Сейчас код фильтрует: `[it for it in items if not self._db.file_exists(it["path"])]` — только новые. Меняем на: если файл есть в БД со статусом `downloaded` и MD5 не совпадает → авто-скачивание.

**API-затраты:** 1 запрос/мин (уже есть) + 1 `get_meta()` на каждый изменённый файл для верификации.

**Плюсы:**
- Минимальные изменения (доработка `_on_poll_result`)
- Ноль дополнительных запросов в отсутствие изменений
- Задержка: файл обнаружен в течение 1 минуты после изменения в облаке

**Минусы:**
- `/resources/last-uploaded` имеет ограничение: возвращает **до 50** последних записей. Если за минуту изменилось >50 файлов — часть пропустится.
- Зависит от правильной работы эндпоинта (документация не гарантирует, что modification туда попадает — может быть только upload)

**Сложность:** ★☆☆ (несколько часов)

---

### Вариант B: Периодический `get_all_files()` — полная MD5-сверка

**Идея:** Раз в N минут вызывать `GET /resources/files` (все файлы плоским списком с пагинацией), для каждого скачанного файла сравнить MD5 с локальным. Если не совпадает — обновить.

**API-затраты:** 1 запрос на 200 файлов (пагинация). Для 1000 файлов = 5 запросов. Плюс на каждый несовпавший файл — 1 запрос для получения download URL.

**Плюсы:**
- 100% гарантия: ничего не пропустит
- Единый «источник истины» — список всех файлов диска

**Минусы:**
- Высокая API-нагрузка: полный проход 1000 файлов = 5 запросов = ~400-800мс каждые N минут
- Дорого на больших дисках (10K+ файлов)
- `get_all_files` делает пагинацию последовательно, пока не кончатся страницы — блокирующая операция

**Сложность:** ★★☆ (1-2 дня)

---

### Вариант C: Ленивая проверка при навигации (folder-level sync)

**Идея:** Когда пользователь открывает папку, для каждого видимого скачанного файла сделать `get_meta(path)` и сравнить MD5. Если не совпадает — скачать новую версию. Использовать существующий механизм MetaFetchThread (конкурентность 8).

**API-затраты:** 1 запрос на каждый файл в открытой папке. Для типичной папки (20-50 файлов) — 20-50 запросов, конкурентно (8 потоков) ≈ 3-6 раундов = ~500мс.

**Плюсы:**
- Нулевая фоновая нагрузка (только когда пользователь смотрит файлы)
- Использует существующую инфраструктуру (MetaFetchThread, concurrent 8)
- Мгновенная реакция на изменения при навигации

**Минусы:**
- Изменения не обнаруживаются, пока пользователь не откроет папку
- Пользователь может не заметить, что файл обновился (анимация?)

**Сложность:** ★★☆ (1-2 дня)

---

### Вариант D: Гибрид (A + C) — рекомендуемый

**Идея:** Комбинация двух подходов:
1. **Расширенный `_poll_cloud`** (вариант A) — быстро ловит изменения, сделанные через другие интерфейсы. Задержка ≤1 мин.
2. **Ленивая проверка при навигации** (вариант C) — подстраховка на случай, если `last-uploaded` не включает modification события.

**API-затраты:** Как A + как C, но суммарно приемлемо.

**Плюсы:**
- Быстрое обнаружение через polling + надёжность через lazy-check
- Использует существующие механизмы (MetaFetchThread, _poll_cloud)
- Нет необходимости в полном сканировании всех файлов

**Минусы:**
- Средняя сложность реализации
- При первом открытии папки может быть задержка из-за N запросов `get_meta`

**Сложность:** ★★☆ (2-3 дня)

---

### Вариант E: Pull-to-refresh (пользовательская кнопка)

**Идея:** Кнопка «Обновить» уже существует и делает `refresh_current()`. Улучшить её: при нажатии обновлять не только список файлов из API, но и проверять MD5 скачанных файлов в текущей папке. Никакой автоматики.

**API-затраты:** Только когда пользователь нажал кнопку.

**Плюсы:**
- Почти ноль изменений в коде
- Нет фоновой API-нагрузки
- Пользователь сам решает, когда синхронизироваться

**Минусы:**
- Не автоматически — пользователь должен помнить нажать кнопку
- Не отвечает требованию «изменил в облаке — подхватилось само»

**Сложность:** ★☆☆ (несколько часов)

## 🔮 Рекомендация: Вариант D (гибрид)

### Почему

1. **Минимальный API footprint** — не делает лишних запросов, когда нет изменений
2. **Быстрое обнаружение** — polling ловит изменения в течение минуты
3. **Полнота** — lazy nav подхватывает то, что пропустил polling
4. **Максимальный reuse** — использует `_RecentFilesThread`, `MetaFetchThread`, `_start_download`, `_pend_upload` — существующие механизмы

### План реализации (≈2-3 дня)

**Фаза 1: Расширенный polling (1 день)**

1. В `_on_poll_result()` изменить логику: вместо отбрасывания всех существующих файлов, проверять `downloaded` файлы на изменение MD5
2. Если MD5 изменился:
   - Если локальный файл не изменялся (статус `downloaded`) — скачать новую версию через `_start_download()`
   - Если локальный файл тоже изменён (`modified`) — вызвать `_handle_conflict()`
3. Ограничить количество авто-скачиваний за один poll (10 файлов)

**Фаза 2: Lazy nav (1 день)**

4. В `_load_folder_local()` после загрузки списка из БД — запустить фоновые MetaFetch для всех `downloaded` файлов в папке
5. При несовпадении MD5 — скачать новую версию (если локально не изменён)
6. Отображать индикацию (статус `syncing` → `downloaded` с обновлённым содержимым)

**Фаза 3: Конфликты и настройки (0.5 дня)**

7. Если файл изменился и локально, и в облаке — показать конфликт-диалог (существующий)
8. Настройка: интервал polling'а + опция «авто-синхронизация изменений из облака»

### Ключевые технические моменты

- **MetaFetchThread** уже умеет параллельно получать MD5 (конкурентность 8)
- **`_start_download()`** — существующий и протестированный механизм
- **`_handle_conflict()`** — существующий диалог разрешения конфликтов
- Polling интервал сейчас 60с (`POLL_INTERVAL_MS = 60000` в `ui_shared.py`)
- Лимит API 40 запрос/сек — при lazy nav папки из 40 файлов вызовет 40 `get_meta` примерно за 1 сек (8 потоков × 5 раундов × 125мс = 1с)

### Что не рекомендуется

- **Вариант B** — полный перебор всех файлов каждые 5 минут: дорого и не нужно при типичном использовании
- **Вариант E** — отсутствие автоматики не соответствует пользовательскому запросу
