## 1. Введение и цели

### 1.1. Что это

Десктопный клиент для Яндекс.Диска под **Windows 10/11**, написанный на **Python + PySide6**. Основной сценарий — **on-demand синхронизация**: файлы видны в облаке, скачиваются по требованию (по двойному клику), изменения отслеживаются и автоматически загружаются обратно в облако.

### 1.2. Ключевые отличия от официального клиента

| | Официальный Яндекс Диск 3.0 | YaDisk Manager |
|---|---|---|
| **Стоимость** | Требуется подписка Яндекс 360 для скачивания/загрузки | **Бесплатно** — использует публичный REST API |
| **Синхронизация** | Автоматическая фоновая (Selective Sync) | On-demand + ручная (двойной клик → скачать) |
| **UI** | Нативное Win32 окно с деревом + таблицей | PySide6 (Qt), только Windows 10/11 |
| **Скриншоты** | Встроенный редактор с горячими клавишами | ❌ Не реализовано |
| **Заметки** | Rich-text редактор, до 500 заметок | ❌ Не реализовано |
| **Dropzone** | Область поверх окон для drag&drop | ❌ Не реализовано |

### 1.3. Почему это вообще работает

Яндекс предоставляет публичный REST API (`cloud-api.yandex.net/v1/disk`) с методами для просмотра, скачивания, загрузки и управления файлами. Ограничение бесплатного тарифа — **5 ГБ** места (см. `README.md`); API не требует подписки.

### 2.2. Лог и локализация

YaDisk Manager использует **три обработчика лога**:

- **Файловый** (`RotatingFileHandler` в `main.py`) — пишет в `%APPDATA%\yadisk-client\yadisk.log`
- **GUI** (`LogHandler` в `ui_log.py`) — отправляет отформатированные строки в `LogWindow` (отдельное окно с чёрным фоном, авто-прокруткой, раскраской по уровню)
- **Консоль** (StreamHandler) — для dev-режима (`python main.py`)

Все три используют **`l10n.LogTranslatingFormatter`** — наследник `logging.Formatter`, который до подстановки аргументов заменяет английский шаблон на русский перевод (см. `l10n.py`, словарь `LOG_RU`, ~230 шаблонов). Плейсхолдеры `%s`, `%d`, `%(name)s` сохраняются — правки в вызовы `logger.*` не нужны.

Язык лога задаётся в `config.json` (`log_lang`, по умолчанию `ru`). `"en"` отключает перевод. Функции `db.get_log_language()`/`set_log_language()`. Для добавления нового языка достаточно скопировать `LOG_RU`, перевести значения и зарегистрировать в `TRANSLATIONS` — см. `LOG_LOCALIZATION.md`.

### 2.3. Диагностика зависаний и нативных падений

Кроме `yadisk.log` приложение ведёт два вспомогательных файла в `%APPDATA%\yadisk-client\` (ротация ~1 МБ → `*.old`):

| Файл | Кто пишет | Что внутри |
|------|-----------|------------|
| `crash.log` | `main.py`: `faulthandler.enable(file=..., all_threads=True)` + Qt-сообщения Critical/Fatal обычной записью в файл | При нативном падении (access violation, heap corruption) — Python-стеки **всех** потоков на момент сбоя. В frozen exe stderr теряется, поэтому Qt Fatal-причина дублируется сюда же |
| `freeze.log` | `ui._dump_all_threads()` — `faulthandler.dump_traceback(file=..., all_threads=True)` | Дамп стеков всех потоков в момент «зависания» UI (heartbeat главного потока не обновлялся >500 мс) |

**Почему не `sys._current_frames()` + `traceback.format_stack()`** (v0.12.3 и раньше): этот способ строит Python-объекты чужого потока и читает исходники с диска, пока заблокированный главный поток держит GIL — на реальной машине это давало нативное падение (0xc0000005) ровно в момент логирования зависания, и лог обрывался без следов. `faulthandler` работает на уровне C и переживает такое состояние.

Монитор зависаний (`MainWindow._freeze_monitor`, daemon-поток): heartbeat главного потока обновляется классом-таймером, монитор проверяет его каждые 200 мс. Сообщение `⚠️ FREEZE: UI blocked for ~%d ms` пишется **один раз за эпизод** (раньше — каждые 200 мс, лог раздувался до десятков МБ), дамп стеков уходит в `freeze.log`, по разблокировке — `✅ FREEZE ENDED: UI was blocked for ~%d ms` с пиковой длительностью.

### 3.4. Таблица файлов (справа)

| Колонка | Описание | Сортировка |
|---|---|---|
| **Имя** | Иконка эмодзи + имя файла/папки | По умолчанию ↑ (возрастание), папки первыми, «..» всегда на первом месте |
| **Размер** | Человекочитаемый (B/KB/MB/GB) | Числовая |
| **Тип** | Описание типа как в Проводнике Windows: папки → «Папка с файлами», распространённые расширения → русские описания («JPEG-изображение», «Документ PDF»…), редкие → реестр HKCR (кэш), неизвестные → «Файл XYZ» | По алфавиту (строковая) |
| **Изменён** | `dd.MM.yyyy HH:mm` | Первый клик ↓ (сначала новые), повторный клик переключает Asc↔Desc |

> **Сортировка:** Используется `QSortFilterProxyModel` с кастомным `lessThan()`.
> Проблема: `dynamicSortFilter=True` заставляет `sort()` работать через zero-timer
> (`_q_sort`), из-за чего таблица отрисовывается до фактической сортировки (фликер).
> Решение: отключать `dynamicSortFilter` перед `set_path()`, сортировать синхронно,
> включать обратно — см. `_sort_table_sync()`.
> 
> При сортировке папки всегда выше файлов, «..» — всегда первый.
> Дефолт: колонка 1 (Имя) Ascending. Колонка 4 (Изменён): первый клик → Descending.
>
> **ВАЖНО:** `RowHoverDelegate._paint_name_cell()` читал `src._items[index.row()]`,
> где `index` — ПРОКСИ-индекс (отсортированный), а `_items` индексируется по
> SOURCE-строкам (порядок из БД/API). После сортировки proxy row ≠ source row →
> делегат брал неправильный элемент, рисуя неверное имя для каждой строки.
> Фикс: `model.mapToSource(index)` перед обращением к `_items`.
> 
> В версии 0.6 этой проблемы не было, т.к. эмодзи были встроены в `DisplayRole`
> строкой `f"{icon} {item['name']}"`, и делегат не переопределял paint() для колонки имени.
| **Статус** | ☁️ в облаке / 💾 на компьютере / ✏️ изменён | downloaded → modified → cloud_only |

- `FileTableSortModel(QSortFilterProxyModel)` — фильтр по **имени** (колонка 1), регистронезависимый
- Приоритет сортировки: `..` всегда первый → папки (независимо от направления) → содержимое
- **Отображение имён файлов** — эмодзи-иконка + имя. Иконка рендерится как текст в кастомном делегате (`RowHoverDelegate._paint_name_cell`), не как `QPixmap` — это предотвращает обрезку по краям. Длинные имена обрезаются с многоточием **посимвольно** через `fontMetrics.elidedText()`. `wordWrap = False` — чтобы элизия не пыталась делить по словам.
- `sort(column 3, Ascending)` → первый раз сбрасывается в `Descending`. При повторном клике Qt сама переключает Asc↔Desc
- `ExtendedSelection` — множественное выделение
- `setSortingEnabled(True)` — по дефолту колонка 1 (Имя) ↑ Asc
- Двойной клик: скачать + открыть, или открыть папку
- Подсветка при наведении — через `RowHoverDelegate (QStyledItemDelegate)`: Highlight с `setAlpha(50)`
- Контекстное меню (правый клик): ✅ Сохранить на компьютере / ☁️ Оставить только в облаке (в зависимости от статуса выделения), 🔗 Скопировать ссылку, ✏️ Переименовать, 📂 Открыть в Проводнике (только если есть локально), 🌐 Просмотреть на сайте (открывает файл/папку на disk.yandex.ru), 🗑 Удалить. **ПКМ не снимает предыдущее выделение**, добавляет текущий элемент к выделению
- **Ширина столбцов**: статус=28px (Fixed, нельзя изменить ширину), имя=300px, размер=ResizeToContents, изменён=100px. Остальные — Interactive
- **Разделители заголовков**: `border-right: 1px solid palette(Midlight)`
- **Выделение через Ctrl+A** не включает «..»
- **Подсветка элементов в древе папок** — аналогичная подсветке в таблице (серый/прозрачно-синий фон)
- **Элемент `..`** — первая запись в таблице для перехода в родительскую папку; не участвует в определении кнопки-переключателя (не влияет на «Сохранить/Оставить»)

### 3.5. Синхронизация выделения между панелями

Выделение в дереве папок и таблице файлов — **взаимоисключающее**:

- При выделении **любого элемента в таблице** → выделение в дереве **снимается** (и наоборот)
- При **клике по пустому месту в любой панели** → выделение **снимается в обеих панелях** сразу
- Механизм: `_on_tree_selection_changed` и `_on_table_selection_changed` вызывают `clearSelection()` противоположной панели
- Защита от рекурсии: флаг `_selection_updating` блокирует повторный вход
- Клик по пустому месту обрабатывается в `eventFilter` (viewport) — чистит обе панели напрямую под `_selection_updating`, так как `clearSelection()` без текущего выделения не эмитит `selectionChanged`
- При навигации («..», Backspace, Enter по папке) — дерево чистится явно перед `_navigate_to_folder`

### 3.6. Режим крупных значков

В правой части окна (справа от прогресс-бара) находятся переключатели режима отображения:
- 📋 Таблица (текущий режим)
- 📦 Крупные значки (альтернативный режим)

В режиме крупных значков файлы и папки отображаются в виде сетки (QListView / QListWidget).
Статус файла отображается иконкой-оверлеем:
- ✅ Белая галочка в зелёном кружочке — сохранён на ПК
- ☁️ Белое облачко с синей обводкой — в облаке
- 🔄 Две белые круговые стрелки в синем кружочке — идёт синхронизация (возможна анимация)

- Иконка: `Assets/icon-16.ico` / `Assets/icon-light-16.ico` (авто-определение тёмной темы), фолбэк — `icon-main.ico`
- **Статус приложения** (`_app_status()` / `_refresh_app_status()`): тултип трея «ЯДиск Менеджер\nВерсия: X.Y.Z\nСтатус: готово / синхронизация / нет соединения / ошибка синхронизации»; в заголовке окна — имя и версия

- **Одиночный клик ЛКМ** по иконке трея — открыть окно (если не в фокусе). Если окно уже в фокусе — ничего не делать.

- **Контекстное меню трея** — постоянный состав: «Показать окно», «Настройки», «Проверить обновления…», «Выход»; не зависит от видимости окна
- **Закрытие окна** (кнопка X) → сворачивается в трей (не завершает процесс), окно лога скрывается вместе с ним (`_hide_log_with_manager()`). Все фоновые процессы (watcher, таймеры, скачивания) продолжают работу.

### 3.8. Диалоги

- **AuthDialog** — инструкция по получению OAuth-токена + инлайн-верификация
- **SettingsDialog** — автозапуск, папка кеша, расположение БД и конфига; **выбор темы** (системная / светлая / тёмная). Тема переключается **live** — при выборе в комбобоксе, без нажатия OK.
- **Конфликт версий (отложенный)** — при одновременном изменении файла локально и в облаке диалог **не открывается сразу**: `_handle_conflict()` только регистрирует конфликт в `_pending_conflicts`, показывает уведомление в трее и кликабельную надпись «⚠️ Конфликт с облаком» в строке состояния. Окно поднимается и диалог выбора открывается по клику по надписи (`_on_conflict_label_clicked()` → `_show_conflict_dialog()`). Выбор: **«Да»** — оставить локальную версию (выгрузить в облако), **«Нет»** — скачать облачную (заменить локальную), **«Отмена»** — конфликт остаётся в очереди. Несколько конфликтов разрешаются по очереди; пока есть конфликт, статус трея — «ошибка синхронизации» с красным бейджем (см. [7.3](#73-стратегия-разрешения-конфликтов))

### 3.9. Оформление и смена темы

Тема оформления реализована через **Fusion + QPalette + единый QSS**:

- `main.py` устанавливает `QStyleFactory.create('Fusion')` сразу после `QApplication()` — до создания любых виджетов
- `_apply_theme_impl()` задаёт одну из трёх палитр (светлая / тёмная / системная) через `app.setPalette()` и применяет **один** общий `app.setStyleSheet(qss)` с hex-цветами (светлый текст `#000000`, тёмный `#FFFFFF`); раньше было 5–6 независимых реполошингов по 500–700 мс каждый, что давало FREEZE/heap corruption
- Полного `unpolish/polish` всех виджетов больше нет — после смены стиля повторно стилизуются только тулбары (дешёво)
- Утверждение «никаких `palette()` в QSS» неверно: в стартовом QSS дерева/таблицы есть `palette(Midlight)`, а `QPalette` явно задаёт `Midlight`, `Highlight` и другие роли; после `_apply_theme_impl()` границы секций переопределяются hex-цветом
- Ховер кнопок — полупрозрачный синий `rgba(64, 150, 255, 0.12)` (не `palette(Highlight)`)

**Цвета тёмной темы:** VS Code / Fluent Design (`#1E1E1E` фон, `#252526` surface, `#094771` highlight, `#007ACC` accent).

**Подсказки (ToolTip):**
- Принудительный QSS: `QToolTip { background-color; color; border }` — так как на Windows QPalette.ToolTipBase может игнорироваться
- Светлая тема: фон `#ffffe5`, текст `#000000`, рамка `#C0C0C0`
- Тёмная тема: фон `#383838`, текст `#CCCCCC`, рамка `#555555`

**Ховер кнопок в панели кнопок:**
- Полупрозрачный синий фон: `rgba(64, 150, 255, 0.12)` (pressed — `0.25`) в QSS
- В светлой теме: светло-голубой оттенок
- В тёмной теме: синеватый оттенок, заметный на тёмном фоне

### 4.2. Статусы файлов

В SQLite хранятся **7 значений** (`db.Database._VALID_STATUSES`, `db.py:888`). `partial` — не статус записи, а вычисляемый агрегат папки:

| Статус | Хранится в БД | Значок (SVG) | Описание |
|---|---|---|---|
| `cloud_only` | Да | `cloud.svg` (☁️) | Только в облаке, локальной копии нет |
| `downloaded` | Да | `loaded.svg` (💾) | Скачан, MD5 совпадает с облаком |
| `modified` | Да | отдельной иконки нет | Локально изменён, MD5 отличается от `last_sync_md5` |
| `syncing` | Да | `synchronize.svg` (🔄) | Файл/папка в процессе скачивания/загрузки |
| `unknown` | Да | `synchronize-light-update.svg` | Статус неизвестен (в т.ч. офлайн-дерево из SQLite) |
| `deleting` | Да | `trash.svg` | Удаление |
| `locked` | Да | `close-ellipse-red.svg` | Файл открыт в другой программе, запись сохраняет `local_path` для повтора |
| `partial` | **Нет** — агрегат папки | `loaded-partically.svg` | Папка содержит и скачанные, и облачные файлы |

## 5. Модель данных

### 5.1. SQLite (таблица `files`)

```sql
CREATE TABLE files (
    cloud_path    TEXT PRIMARY KEY,       -- /Документы/отчёт.docx
    name          TEXT NOT NULL,          -- отчёт.docx
    type          TEXT NOT NULL DEFAULT 'file',  -- file | dir
    mime_type     TEXT,                   -- application/pdf
    size          INTEGER DEFAULT 0,
    modified      TEXT,                   -- ISO 8601 (UTC)
    md5           TEXT,                   -- MD5 в облаке
    last_sync_md5 TEXT,                   -- MD5 при последней синхронизации
    status        TEXT NOT NULL DEFAULT 'cloud_only',  -- 7 значений, без CHECK
    local_path    TEXT,                   -- C:\Users\...\.yadisk-cache\...
    local_mtime   TEXT,                   -- Время последней локальной синхр.
    created_at    TEXT DEFAULT (datetime('now')),
    updated_at    TEXT DEFAULT (datetime('now'))
);
```

CHECK-ограничение на `status` удалено миграцией `db._migrate_drop_check_constraint()` (в старых БД оно блокировало `syncing`, `deleting`, `unknown`); допустимые значения задаёт `_VALID_STATUSES`. Кроме `files`, в БД есть таблицы `search_history` (история поиска) и `pending_ops` (очередь операций).

## 6. API-интеграция

### 6.1. REST-клиент (`disk_api.py`)

Базовый URL: `https://cloud-api.yandex.net/v1/disk`

| Метод API | HTTP | Параметры | Используется для |
|---|---|---|---|
| `GET /` | GET | — | Информация о диске |
| `GET /resources` | GET | path, limit, offset | Навигация по папкам |
| `GET /resources/files` | GET | limit, offset | Все файлы (flat) |
| `GET /resources/last-uploaded` | GET | limit | Polling изменений |
| `GET /resources/download` | GET | path | Получение ссылки на скачивание |
| `GET /resources/upload` | GET | path, overwrite | Получение ссылки на загрузку |
| `PUT /resources` | PUT | path | Создание папки |
| `DELETE /resources` | DELETE | path, permanently | Удаление |
| `PUT /resources/publish` | PUT | path | Публичная ссылка |
| `PUT /resources/unpublish` | PUT | path | Снять публичный доступ |
| `POST /resources/move` | POST | from, path, overwrite | Перемещение/переименование |
| `POST /resources/copy` | POST | from, path, overwrite | Копирование |

### 6.2. Ключевые особенности реализации

- **Rate limiter** (40 запросов/сек) — скользящее окно, предотвращает 429 Too Many Requests
- **Retry с exponential backoff** — для 429 и 503 ошибок
- **AuthError** — детекция 401, перезапрос токена через диалог
- **Нормализация путей** — убирает префикс `disk:`, гарантирует `/` в начале

### 6.3. Корзина и история

- **Корзина** — API поддерживает `DELETE /resources?path=...&permanently=false`. Файлы попадают в корзину Яндекс.Диска, доступную по `https://disk.yandex.ru/client/trash`. Просмотр корзины через REST API возможен (эндпоинт `/trash/resources`). YDM может добавить просмотр и очистку корзины.
- **История изменений** — API возвращает метаданные файла (версия `revision`), но нет публичного эндпоинта для списка изменений по одному файлу. Возможно только через `GET /resources?path=...&limit=1` с пагинацией по истории — требует дополнительного исследования.

## 7. Движок синхронизации

### 7.1. Фазы `full_sync()`

При старте программы (или по кнопке «Синхронизировать»):

```
Phase 1: GET /resources/files (все файлы из облака)
         → cloud_by_path / cloud_by_md5
Phase 2: os.walk(cache_dir)
         Для каждого локального файла:
           Если совпадает MD5 → matched
           Если локальный новее → upload
           Если облачный новее → download
           Если MD5 совпадает с другим путём → move (файл перемещён в облаке)
           Если был downloaded, но удалён из облака → delete локально
           Если новый локальный → upload new
Phase 3: Очистка БД от файлов, помеченных downloaded, но отсутствующих локально
```

Полный обход — только один из механизмов. Изменения, пришедшие из облака, обрабатывает обратная синхронизация (7.4), а исчезнувшие из облака файлы — `VanishedResolveThread` (7.5).

### 7.2. Watchdog (`watcher.py`)

- Использует `watchdog.Observer` (рекурсивный мониторинг), `watchdog.events.FileSystemEventHandler`
- `DEBOUNCE_SEC = 1.0` — кумуляция modified/created-событий (чтобы не дёргаться на каждое автосохранение); `deleted` уходит сразу
- Игнорирует временные файлы (`.filename`, `filename~`, `*.tmp`)
- В UI события попадают в `_pend_upload` и выгружаются через `_schedule_upload_flush()`: `UPLOAD_FLUSH_DELAY_MS = 250`, но при непрерывном потоке событий полное ожидание ограничено `UPLOAD_FLUSH_MAX_WAIT_MS = 1000` (flush на следующем витке event loop)
- Проверки метаданных облака «через 2 секунды» нет: сверка MD5 выполняется `MetaFetchThread` по слоям 7.4, уже после постановки файла в очередь

### 7.3. Стратегия разрешения конфликтов

```
IF cloud_md5 == last_sync_md5:
    → облако не менялось, конфликта нет
ELSE IF local_md5 == last_sync_md5:
    → менялось только облако → безопасное скачивание
ELSE:
    → изменились и локальный файл, и облако → ОТЛОЖЕННЫЙ конфликт:
      _handle_conflict() → _pending_conflicts + уведомление в трее
      + надпись «⚠️ Конфликт с облаком» в статус-баре (окно НЕ поднимается)
      → по клику: _show_conflict_dialog():
        «Да»   — оставить локальную версию (выгрузить в облако)
        «Нет»  — скачать облачную версию (заменить локальную)
        «Отмена» — конфликт остаётся в очереди, диалог можно открыть ещё раз
```

Пока в `_pending_conflicts` есть записи, `_app_status()` возвращает `conflict`: статус трея «ошибка синхронизации» и красный бейдж. Несколько конфликтов разрешаются по очереди (первый в списке).

### 7.4. Обратная синхронизация (облако → локальный кеш)

Три слоя; все сходятся в `_queue_reverse_meta_fetch()` → `MetaFetchThread` (конкурентность 8, `_max_meta_concurrent`) → `_on_reverse_meta_fetched()`:

1. **Poll каждые 60 с** (`POLL_INTERVAL_MS`) — `_poll_cloud()` → `RecentFilesThread` (`GET /resources/last-uploaded?limit=50`) → `_on_poll_result()`: для существующих `downloaded`-файлов сравнивает `md5` с `last_sync_md5`; изменилось только облако → авто-скачивание, изменились оба → `_handle_conflict()`.
2. **Bulk каждые 15 мин** (`BULK_SYNC_INTERVAL_MS = 900000`, плюс разовый запуск через 10 с после старта и при reconnect) — `_start_bulk_sync()` → `AllFilesThread` (500 записей на страницу, 4 параллельных запроса) → `_on_bulk_sync_complete()` → `get_changed_downloaded_files()` → MetaFetch. Параллельно `AllFilesThread.vanished` отдаёт исчезнувшие записи в `VanishedResolveThread`.
3. **Ленивая проверка при навигации** — `_load_folder_local()` / `_on_folder_loaded()` проверяют `downloaded`-файлы открытой папки через тот же MetaFetch.

Если `cloud_md5 == last_sync_md5` — облако не менялось; если `local_md5 == last_sync_md5` — безопасная докачка; иначе — отложенный конфликт (7.3).

**Авто-загрузка новых файлов в synced-папках.** Если все файлы в папке `downloaded`, папка считается «полностью скачанной», и новый файл в ней скачивается автоматически:
1. **Poll (каждые 60 с)** — `_on_poll_result()` проверяет родительскую папку до добавления файла в БД
2. **После full_sync** — `_auto_download_orphans_in_synced_folders()` проверяет все `cloud_only`-файлы

### 7.5. Удаления и перемещения с другого ПК (`VanishedResolveThread`)

`AllFilesThread` (только при полном скане с нуля и непустом облачном списке) отдаёт `vanished` — локально скачанные записи, которых нет в ответе API. `VanishedResolveThread` в фоне считает MD5 и выносит решение, которое применяется в UI-потоке (`_on_vanished_resolved()`):

| Условие | Решение |
|---|---|
| Локальной копии нет | `drop` — удалить запись из БД |
| `md5 == last_sync_md5`, файл не менялся | `delete` — удалить локальную копию и запись |
| Рядом есть облачный файл с тем же MD5 (`find_file_by_md5`) | `move` — перенести локальную копию на новое имя без повторной выгрузки |
| Локально изменён или `status='modified'` | `conflict` → `_handle_remote_delete_conflict()`: «оставить локально» (`modified` + постановка в очередь выгрузки) или «удалить» |

Пути из `_recently_uploaded` (30 с) пропускаются — только что выгруженный файл не считается «исчезнувшим» при устаревшем листинге.

## Изменения v0.12.7 — v0.13.0

### Синхронизация: upload

| Компонент | Что изменилось |
|----------|----------------|
| `UploadWorker.finished(str, str)` | Второй аргумент — MD5 байтов, реально отправленных в PUT (`hashlib.md5()` обновляется в генераторе чанков), а не содержимое файла на момент завершения. `_do_upload.on_finished` кладёт его в очередь результатов как `(cloud_path, local_path, sent_md5, "upload", False)` |
| `MainWindow._process_result_queue()` | Пишет в БД `md5`/`last_sync_md5` = `sent_md5`. Снимок `(size, mtime_ns)` в `_upload_stamps` снимается перед стартом воркера: если после upload он не изменился, `_md5_file()` не вызывается; иначе локальный MD5 сравнивается с `sent_md5`, и при расхождении путь попадает в `_dirty_uploads` |
| `MainWindow._requeue_dirty_uploads()` | Отложенно (`QTimer.singleShot(0)`, уже после записи метаданных текущего upload) переносит dirty-пути в `_pend_upload` и запускает flush — повторная выгрузка без диалога конфликта |
| `_recently_downloaded` / `_recently_uploaded` | Наборы-«глушилки» ложных watcher-событий: скачивание/выгрузка не должна выглядеть локальным изменением. `_recently_uploaded` живёт 30 с и дополнительно отсекает устаревший облачный листинг в `VanishedResolveThread` |
| `UPLOAD_FLUSH_DELAY_MS = 250`, `UPLOAD_FLUSH_MAX_WAIT_MS = 1000` | Debounce авто-выгрузки снижен с 2000 мс; `_schedule_upload_flush()` перезапускает single-shot таймер, но общее ожидание ограничено потолком (при достижении — `start(0)`), чтобы непрерывные события (bulk copy/unzip) не блокировали старт выгрузки. Конфликтная ветка «оставить локально» использует тот же таймер |
| Уведомления об успешной выгрузке | Вызов `_schedule_transfer_notification(..., "upload")` удалён из ветки `upload` `_process_result_queue()`; теперь функция работает только с `kind="download"` и показывает одно агрегированное сообщение через 1.5 с после последнего файла |

### Конфликты (отложенный диалог)

| Компонент | Что изменилось |
|----------|----------------|
| `MainWindow._handle_conflict()` / `_register_conflict()` | Раньше сразу поднимало окно и показывало модальный диалог. Теперь только запоминает конфликт в `_pending_conflicts` (без дублей по `cloud_path`), показывает уведомление в трее и кликабельную надпись «⚠️ Конфликт с облаком» в строке состояния; `_refresh_app_status()` переводит трей в состояние «ошибка синхронизации» |
| `MainWindow._on_conflict_label_clicked()` / `_show_conflict_dialog()` | Диалог открывается по клику по надписи: окно поднимается через `_tray_show()`. Выбор не изменился: «Да» — оставить локальную версию (выгрузить в облако), «Нет» — скачать облачную, «Отмена» — ничего не делать, конфликт остаётся в очереди. Несколько конфликтов разбираются по очереди, `_clear_pending_conflict()` снимает только первый |

### Синхронизация: удаления/перемещения с другого ПК

| Компонент | Что изменилось |
|----------|----------------|
| `Database.sync_children_from_api()` | Возвращает `vanished` — локально скачанные файлы, которых нет в ответе API; в записи добавлен `status`. Сами записи в БД не удаляются: решение принимает `VanishedResolveThread`. Записи `syncing` исключены из prune и vanished |
| `Database.get_local_files_not_in()` | Возвращает `status` вместе с `cloud_path`/`local_path`/`md5`/`last_sync_md5` — для bulk-прохода `AllFilesThread` |
| `Database.find_file_by_md5(md5, parent_path, exclude_path)` | Ищет облачную запись без локальной копии в той же папке — сопоставление перемещения (новое имя, тот же контент) |
| `VanishedResolveThread` (`ui_threads.py`) | Для каждой vanished-записи: локальной копии нет → `drop`; MD5 не менялся → `delete`; найден `find_file_by_md5` → `move`; локально изменён или `status='modified'` → `conflict`. Тяжёлый MD5 считается в фоне |
| `MainWindow._on_vanished_resolved()` | Применяет решения в UI-потоке: `delete` удаляет файл и запись; `move` переносит копию (`os.replace`, при занятой цели — сравнение MD5, чужие данные не перезаписываются), обновляет БД; `conflict` → `_handle_remote_delete_conflict()`. Пропускает пути из `_recently_uploaded` (и `move` в такой путь). Копит `_vanished_pending`, чтобы не плодить параллельные потоки |
| `_handle_remote_delete_conflict()` | «Оставить локально» → `update_last_sync_md5("")`, `status='modified'` и постановка в `_pend_upload` (с debounce); «удалить» → удаление локальной копии и записи |
| `AllFilesThread.vanished` | Сигнал эмитится только при полном скане с нуля (`started_at_zero`) и непустом облачном списке — пустой ответ API не «удаляет» все локальные копии |
