# Дизайн: авто-обход сетевых блокировок (net heal)

- **Дата:** 2026-08-21
- **Статус:** утверждено пользователем (подход A), план не написан
- **Контекст обнаружения:** рабочий ПК пользователя в корпоративной сети — внутренний DNS (10.0.0.10) отдаёт SERVFAIL для `cloud-api.yandex.net` и `s*.storage.yandex.net` при доступном `yandex.ru`; исходящий UDP/53 перехватывается (публичные DNS недоступны напрямую). При этом TCP/443 до реальных IP Яндекса работает — блокировка только на уровне резолвинга. Ручной обход (запись в `hosts`) подтвердил работоспособность.

## Требования

| # | Требование |
|---|---|
| 1 | При детекте DNS-блокировки приложение **один раз** спрашивает «Включить обход?» и запоминает ответ в конфиге; повторных вопросов нет |
| 2 | Кэш IP устаревает по TTL из DNS-ответа и сам перепроверяется при сбоях соединения (CDN-адреса Яндекса ротируются) |
| 3 | Область: DNS-блокировки **и** TCP-сбои (reset/timeout). Если не помогло ничего — нейтральная подсказка про VPN (без упоминания конкретных программ), раз за сессию |
| 4 | Без админ-прав, без UAC, без изменений системных настроек; всё внутри процесса приложения |
| 5 | Пока обычный DNS работает — он в приоритете; обход невидим и включается только при сбое |

## Отклонённые альтернативы

- **B. Авто-правка hosts через elevation** — UAC-промпты, ломается корпоративными политиками, устаревшие записи при ротации CDN-IP ломают доступ задним числом.
- **C. Системный DoH Windows 11** (`netsh`) — только Win11, нужны админ-права, влияет на всю систему, конфликтует с GPO.

## Архитектура

### Новый модуль `net_heal.py` (чистая логика, без Qt)

**`classify_error(exc) -> NetIssue`** — классификатор исключений `requests`/`urllib3`:
- `DnsBlocked` — вложенный `NameResolutionError` / `getaddrinfo failed` / `gaierror`
- `TcpBlocked` — `ConnectionResetError`, `ProtocolError`, таймаут соединения
- `None` — прочее (HTTP-коды, SSL-сертификаты и т.п. классифицируются как обычные ошибки)

**`DoHResolver`** — DNS-over-HTTPS JSON (RFC 8484-совместимый JSON-формат):
- Эндпоинты по голому IP (сертификаты обоих валидны без DNS): `https://1.1.1.1/dns-query?name=<host>&type=A`, фолбэк `https://8.8.8.8/resolve?name=<host>&type=A`
- Таймаут 5 с на эндпоинт; возвращает список A-записей или `[]`
- Использует собственный `requests` без монтирования HealedAdapter (иначе рекурсия)

**`IpCache`** (потокобезопасен, `threading.Lock` — вызывается из воркер-потоков):
- `host -> (ips: list[str], expires_at: float)`; TTL из DNS-ответа, зажат в `[60 .. 3600]` секунд
- Отрицательное кэширование: IP, на котором соединение упало, помечается плохим до конца TTL → следующий IP списка / перерезолв
- Инвалидация всего кэша при смене «здоровья» сети не нужна: обычный DNS всегда пробуется первым

**`HealedAdapter(HTTPAdapter)`** — монтируется на сессию вместо стандартного:
- Резолв хоста: сначала системный DNS; при ошибке (или если включён режим обхода и есть свежий кэш) — `IpCache`/`DoHResolver`
- Соединение открывается на полученный IP, но TLS-рукопожатие идёт с `server_hostname=<исходный хост>` (SNI), проверка сертификата не отключается
- После исчерпания ретраев бросает типизированную `NetBlockError(kind, host)` вместо сырого `ConnectionError`

### Интеграция

- **`disk_api.py:67-69`** — единственная точка: `self._session.mount("https://", HealedAdapter(...))`. Покрывает API-вызовы, скачивания (`ui_workers.py:42,161`) и загрузки (`ui_workers.py:133`)
- **`updater.py` не трогаем** — GitHub-трафик, другая проблемная зона
- **`config.json`** (через `db.py`): флаг `net_heal_enabled: true | false | null`; `null` = ещё не спрашивали
- **`ui.py`:**
  - первый `NetBlockError(DnsBlocked)` при `net_heal_enabled is null` → уведомление в трее/диалог «DNS заблокирован. Включить обход?» → запись флага → дальше молча
  - `NetBlockError(TcpBlocked)` после всех попыток → раз за сессию подсказка «Доступ к Яндекс.Диску ограничен сетью. Попробуйте VPN»
  - Сигнальный мост: net_heal не знает про Qt; UI реагирует на исключения в обработчиках воркеров (паттерн существующий)
- **Настройки (`ui_dialogs.py`):** чекбокс «Обход DNS-блокировок» — меняет флаг вручную; выключение = поведение как раньше

### Поток данных (пример: скачивание файла)

```
DownloadWorker → api._session.get(storage_href)
  → HealedAdapter: getaddrinfo(s41nrg.storage.yandex.net) → SERVFAIL
  → IpCache пуст/протух → DoHResolver(1.1.1.1) → [37.140.178.41], TTL 300с
  → TCP на 37.140.178.41:443, TLS SNI=s41nrg.storage.yandex.net, сертификат OK
  → ответ стримится; IP лежит в кэше для следующих запросов
```

Если DoH тоже недоступен (файрвол режет 1.1.1.1 и 8.8.8.8) → `NetBlockError` → подсказка про VPN.

## Обработка ошибок

- Все сетевые исключения внутри адаптера классифицируются один раз; наружу — только `NetBlockError` либо оригинальное исключение (если не сетевое)
- Ретраи между эндпоинтами DoH и IP из списка — по одному кругу, без экспоненциальных задержек (лимит API 40 rps не задевается: DoH-запросы идут к сторонним resolver'ам)
- Логирование через существующий `logging` (`logger = logging.getLogger("net_heal")`): факты блокировки, применённые IP, истечения TTL — INFO; неудачи DoH — WARNING

## Тесты (без реальной сети)

| Что | Как |
|---|---|
| `classify_error` | параметризованные моки исключений requests/urllib3 |
| `DoHResolver` | мок HTTP-ответов JSON; фолбэк со второго эндпоинта; таймаут |
| `IpCache` | TTL-истечение (подмена time.monotonic), вытеснение плохих IP, потокобезопасность (N потоков) |
| `HealedAdapter` SNI | мок сокета: проверка, что `wrap_socket` получает `server_hostname=исходный хост`, а коннект — на IP из кэша |
| Интеграция disk_api | мок транспорта: первый запрос падает getaddrinfo → второй идёт на закэшированный IP |
| UI-реакции | существующие паттерны тестов MainWindow: однократность подсказки за сессию |
