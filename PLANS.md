## 🐞 Открытые баги

### 🔴 Критично / часто встречается

- **WinError 5 при удалении папки** — «Не удалось удалить YaDiskManager: [WinError 5] Отказано в доступе: 'D:/YandexDiskTestFolder\Sync/YaDiskManager'». Возможно, папка открыта в Проводнике или другом приложении. Разобраться и предложить решение. *(см. Планы 2.2)*

### 🟡 Средний приоритет

- **Молчаливое падение на чужой машине** — лог обрывался ровно на `⚠️ FREEZE`, процесс умирал с 0xc0000005 без traceback. Причина найдена и закрыта в v0.12.4 (монитор зависаний строил Python-фреймы чужого потока под GIL → нативный краш; теперь `faulthandler.dump_traceback` в `freeze.log`). **Требуется подтверждение на той машине:** при повторном падении в `crash.log`/`freeze.log` появятся стеки всех потоков
- **Нет индикации удаления** — после инициирования удаления файла/папки нет никакой индикации. Ожидание: удаляемым элементам (и их родителям/детям) присваивается статус «синхронизация», затем удаление из интерфейса после подтверждения из облака и обновление статусов родителей.
- **Скачивание пустой папки** — ошибка «Выделите файлы или папки для скачивания или удаления локальной копии». При этом папка, в которой есть одна пустая подпапка и все файлы скачаны, помечается как «на компьютере».
- **«Оставить только в облаке» / «Сохранить на компьютере» с выделением файлов и папок** — действие применяется только к папкам, но не к файлам.
- **Выгрузка начинается до завершения полной загрузки данных из облака** — вопрос: это нормально? (возможно, стоит дожидаться завершения).
- **История поиска: показывается не всегда** — при некоторых условиях при нажатии на панель поиска показывается 1–2 последних запроса вместо пяти; последние результаты не показываются, когда фокус на панели поиска и в неё ничего не введено (например, выделить весь текст и удалить, или нажать крестик).
- **Контекстное меню строки поиска англоязычное** — Undo, Redo, Cut, Copy и т.д.; нужно русскоязычное.
- **Быстрая навигация по Дереву папок** — содержимое панели загружается быстро при навигации; можно ли сделать такую же быструю навигацию по дереву? *(идея/вопрос)*

### 🔵 Низкий приоритет

- **Ctrl+A выделяет «..»** — ломает логику кнопок «Сохранить»/«Оставить». *(= Планы 2.5)*
- **Разделители колонок** — столбец «Размер» заблокирован; последний столбец без правой границы. *(= Планы 2.12)*
- **ЗАВИСАНИЕ 577 мс при `_hide_table_loading`** — `self._table_stack.setCurrentIndex(1)` после `ApiListThread: / -> 30` блокирует UI на полсекунды (стек `event() → _on_folder_loaded → _hide_table_loading`). Проверить, не запускается ли там тяжёлая операция (например, `refresh_statuses()` на 100К+ файлов под локом)

#### 3.8 Детали: ложный конфликт после выгрузки

**Сценарий:** файл `a.txt` скачан → пользователь меняет его на ПК (версия A) → watcher запускает upload → пока upload идёт (или сразу после), пользователь сохраняет ещё раз (версия B) → Менеджер видит: локально MD5(B), в облаке MD5(A) → объявляет конфликт.

**Ожидание:** версия B выгружается следующим проходом, диалога конфликта нет. MD5, который записывается в БД как `last_sync_md5`, должен быть MD5 **фактически отправленных байт** (A), а не файла на момент завершения upload (B). Если после завершения upload локальный MD5 ≠ отправленному — файл помечается «грязным» и ставится в очередь повторно.

#### 3.9 Детали: синхронизация удалений/перемещений между ПК

**Сценарий:** аккаунт на ПК-A и ПК-B, оба ПК держат локальный кеш. На ПК-A пользователь удаляет `photos/1.jpg` (или перемещает `photos/1.jpg` → `archive/1.jpg`). На ПК-B файл остаётся на месте; его `last_sync_md5` совпадает, watcher молчит, и при следующей сверке он выгружается обратно в облако — файл «воскресает».

**Ожидание:** при чтении облачного листинга (bulk-обход `AllFilesThread` и ленивая навигация по папке; poll `last-uploaded` видит только новые/изменённые файлы и исчезнувшие не возвращает) записи, которых больше нет в облаке, но которые есть локально со статусом `downloaded`, разрешаются так:
- **удаление** — локальная копия удаляется, запись БД удаляется;
- **перемещение** — если в той же облачной папке появился новый файл с тем же MD5, локальная копия перемещается по новому пути, запись БД обновляется;
- **конфликт** — если локальная копия изменена после последней синхронизации (MD5 ≠ `last_sync_md5`), спрашиваем пользователя (в offscreen-режиме — авто-«оставить локально»);
- свежевыгруженные файлы (≈30 с после upload) не считаются исчезнувшими — защита от устаревшего API-листинга.

#### 3.10 Детали: журнал версий MD5 вместо постоянного полного обхода

**Концепция (пользователь, запись с его слов):** программа сама ведёт журнал изменений файлов с MD5, чтобы понимать, что файл сейчас в облаке — это предыдущая версия файла, который сейчас на диске и изменён; тогда конфликта нет, а есть обычная выгрузка новой локальной версии. Полный обход `AllFilesThread` делать один раз при первом подключении к облаку, дальше — вести историю с ограниченным максимумом и подгружать последние изменённые файлы из облака порциями (~200). Если часть порции уже есть в журнале — новые записи дописать; если ни одна запись порции не совпала с журналом — подгрузить ещё 200 и так далее, пока не найдётся точка опоры.

**Как предлагаю реализовать (решение агента, не согласовано отдельно):**
- таблица SQLite `file_versions` (`cloud_path`, `md5`, `seen_at`), индекс по `(cloud_path, md5)`; каждая запись ~100 байт;
- максимум: **20 версий на файл и 10 000 записей всего** (≈1 МБ на диске, запрос по индексу — O(log n)); при переполнении старые записи удаляются FIFO. Этого хватает, чтобы покрыть 50 страниц по 200 файлов и не нагружать ни БД, ни UI;
- первый успешный контакт с облаком → один полный `AllFilesThread`, журнал инициализируется текущими MD5 (текущая точка опоры);
- дальше инкрементально: `GET /resources/last-uploaded?limit=200` (текущий poll использует `limit=50`), для каждой записи проверять `(cloud_path, md5)` в журнале; неизвестные дописывать; если за страницу не нашлось ни одной известной записи — брать следующую страницу (`offset`) вплоть до потолка числа страниц;
- при разрешении расхождения: если облачный MD5 присутствует в журнале как предыдущая версия этого же пути, а локальный файл изменился → считать это «облако отстаёт» и выгружать локальную версию без диалога конфликта; если облачный MD5 в журнале отсутствует — это чужое изменение, требующее обычной сверки/конфликта.
