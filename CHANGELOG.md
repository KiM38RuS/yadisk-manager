# Changelog

## [Unreleased]

### Исправлено
- **Ложный конфликт после повторного локального изменения во время выгрузки** (PLANS 3.8): `UploadWorker` возвращает MD5 фактически отправленных байтов, очередь результатов и `_dirty_uploads` сравнивают локальный файл с этой версией; изменение, случившееся во время upload, помечается dirty и выгружается повторно без диалога. После завершения upload файл не хешируется повторно, если `(size, mtime_ns)` не изменился (`_upload_stamps`); полное сравнение MD5 выполняется только тогда, когда stat изменился.
- **Удаления и перемещения с другого ПК применяются локально** (PLANS 3.9): `sync_children_from_api()` и `get_local_files_not_in()` отдают `status`, `VanishedResolveThread` удаляет локальную копию, а при совпадении MD5 (`find_file_by_md5`) переносит её на новое облачное имя вместо повторной выгрузки; `_recently_uploaded` (30 с) защищает только что отправленные файлы, «оставить локально» пишет `status='modified'`.
- **Watchdog не видел новые файлы, созданные вне Менеджера** (PLANS 3.5): в `MainWindow._handle_file_created()` путь нормализуется `os.path.normcase(os.path.abspath(...))`, принадлежность кешу проверяется по префиксу с `os.sep` (корректно и для корня диска), `rel in ("", ".")` отбрасывается.
- **Авто-загрузка изменённого файла стартовала не сразу** (PLANS 3.6): debounce снижен с 2000 до 250 мс (`UPLOAD_FLUSH_DELAY_MS`), при непрерывных watcher-событиях общее ожидание ограничено 1000 мс (`UPLOAD_FLUSH_MAX_WAIT_MS`) с принудительным flush; конфликтная ветка после «оставить локально» использует тот же debounce.
- **Офлайн-старт показывал пустое дерево** (PLANS 3.7): при отсутствии сети дерево строится из SQLite (`populate_children_from_db(..., status_override)`), корень раскрывается, спиннер скрывается; переподключение обновляет только дерево, не сбивая таблицу и текущую папку.

## v0.12.6 (2026-10-22)

- **Исправлено (критическое)**: авто-обновление «скачивалось, приложение закрывалось — и тишина». `updater.apply_update()` запускал `apply_update.bat` с `creationflags = 0x08000000 | 0x00000004`, подписанными как `CREATE_NO_WINDOW | DETACHED_PROCESS`, но `0x4` — это `CREATE_SUSPENDED`, а `DETACHED_PROCESS` = `0x8`. В итоге `cmd.exe` рождался **приостановленным**: bat не выполнялся ни разу, старый exe не переименовывался, новый (`YaDiskManager.new.exe`) оставался лежать рядом, перезапуска не происходило. Баг жил с v0.11.6 (когда появился `apply_update`) во всех выпущенных сборках
  - Фикс: `creationflags=subprocess.CREATE_NO_WINDOW | subprocess.DETACHED_PROCESS` — именованные константы вместо магических hex-чисел, чтобы флаг снова не «переехал»
  - Диагностический признак зомби-процесса: `cmd.exe` в состоянии `WaitReason=Suspended`, CPU = 0, ~2 handles, **без** дочернего `ping.exe` (в нормальном сценарии bat запускает `ping` как паузу перед переименованием). Лечится kill'ом зависшего `cmd.exe`
- **⚠️ Важно при обновлении с ≤0.12.5**: эти версии несут баг, поэтому обновиться «из трея» они не смогут — скачают `YaDiskManager.new.exe` и замолчат. Ручное лечение: закрыть приложение и запустить появившийся рядом `apply_update.bat` (он переименует exe и запустит новую версию), либо скачать `YaDiskManager_v0.12.6_portable.exe` с GitHub Releases вручную. Начиная с 0.12.6 авто-обновление снова работает
- **Тесты**: `tests/test_updater.py` — новый класс `TestApplyUpdateCreationFlags` (3 теста: флаги не содержат `CREATE_SUSPENDED` (0x4); флаги равны ровно `CREATE_NO_WINDOW | DETACHED_PROCESS`; `apply_update.bat` пишется рядом с exe) — всего **307** тестов
  - Проверено воспроизведением: со старыми флагами `cmd.exe` висит в `Suspended` и bat не выполняется; с новыми — bat отрабатывает за ~4 с (переименование + `start`)

## v0.12.4 (2026-10-18)

- **Исправлено (критическое)**: нативное падение приложения (0xc0000005) — лог обрывался ровно на `⚠️ FREEZE`, процесс умирал молча:

## v0.12.3 (2026-10-17)

  - Теперь `maxsize=POOL_SIZE` (30) доходит до пула: сигнатура `HealedAdapter.init_poolmanager` сделана явной (`connections, maxsize, block=False, **pool_kwargs`), как в `requests.adapters.HTTPAdapter`
- **Исправлено (безопасность)**: OAuth-токен Яндекса больше не уходит на api.github.com — `YaDiskAPI` использует собственную `requests.Session` вместо общей процессной; `get_shared_session()` осталась для `updater` (PLANS 2.17)
